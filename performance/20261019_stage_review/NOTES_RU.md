# Повторная проверка этапов оптимизации

Этот каталог относится к новой общей серии на **50 модельных мс**. Источник
таблиц — `measured/runs.json`; предыдущие каталоги измерений читаются как
исторические свидетельства и не перезаписываются. Производственная сборка
Network Studio не изменяется в рамках этой проверки.

## Что можно сравнивать

- Direct solve: S0 исходный решатель → S1 кэши → S2 компактное ядро →
  S3 прямой вызов ядра из версии с runner. Все четыре используют один поток.
- P1 ресурсы, P2 токи, P3 STDP: сохранённые промежуточные EXE, явно четыре
  вычисляющих потока. Переход S3→P1 включает изменение политики исполнения,
  поэтому его отношение времён нельзя выдавать за ускорение одной формулы.
- `control_no_roots4` — **новая абляция финальной реализации**: при четырёх
  потоках отключён только параллельный поиск корней. Это не исторический P4.
  Её сравнение с `p5_final4` изолирует изменение этой настройки; сравнение
  `p5_final4`→`p5_final8` показывает эффект числа потоков той же реализации.
  P3→control включает совокупность промежуточных правок; выделить из него
  вклад P4 нельзя, поскольку исторический непрофилируемый P4 EXE не сохранён.
- Сохранённые profile stage4 и final измеряются при одинаковых четырёх
  потоках, но составляют отдельную таблицу со включёнными счётчиками.
  Профильное время не смешивается с обычным Release. Исторический профиль
  не заменяет исходники этапа и не делает абляцию историческим P4.
- GUI: исходная, compact, runner и final8 версии имеют собственный wall
  timer. Они сравниваются между собой, а не с solve time. Используется
  скрытое настоящее окно Win32/DX11/Present(1); это не ручная сессия видимого
  приложения и не измерение времени GPU. Окклюзия и статусы Present сохраняются.
  Wall охватывает цикл расчёта до подтверждённого завершения. Setup, экспорт
  и checkpoint исключены из wall, но входят в отдельный process_seconds.

В новой серии по три повтора, кроме исходного GUI (один). Таблицы должны
показывать фактическое n, медиану, min/max, выборочное SD и память. При n=1
SD не определено. Сокращение времени, рассчитанное из разных длительностей,
разных таймеров или разных режимов profiling, не является измеренным
инкрементальным ускорением.

## Проверки и ограничения

Сеть — документированная производная сохранённого примера: 500 нейронов
Ижикевича, 400 E / 100 I, **15 013** TM-связей, мультипликативная STDP,
σ = 5, seed = 706, dt = 25 мкс, интервал шума 1 мс. Это не точная
идентификация исходной сети примерно из 15 041 связи. Сохранённый план стадий
в benchmark не активируется.

Численная эквивалентность подтверждается отдельными `comparison_*.json`:
десять CSV побайтно, для одинаковой сборки — весь checkpoint, для разных
сборок — весь payload и прочие поля за исключением build ID и зависимой
контрольной суммы. Исходные checksum, schema, algorithm и config проверяются;
несовместимые checkpoint не загружаются ради обхода защиты. Генератор отчёта
проверяет сохранённые свидетельства, а не пересчитывает модель.

Память относится ко всему процессу, включая setup, экспорт и checkpoint.
OS PeakWorkingSet — максимум до последнего успешного опроса; sampled
PrivateUsage может пропустить краткий пик и не называется точным lifetime
peak. Порядок запусков фиксирован, температура и сторонняя нагрузка не
контролируются. На других CPU/ARM оптимальное число потоков может отличаться.

Свежий `ctest.xml` относится к текущей финальной реализации. Для P1–P3
сохранены benchmark EXE, но нет полного набора исторических unit-test EXE
и отдельных снимков исходников. Новое численное сравнение этих EXE не
заменяет недостающую полную историческую тестовую матрицу.

Ранние отчёты сохраняются с первоначальным результатом: preliminary 3/4
(`invalid delivery timestamp or disabled edge`), stage4 25/27
(`lost or extra delivery`, GUI `Izhikevich parameters are missing`),
stage5 8/8, прежний final 28/28. Старые неудачи не объявляются успешными
задним числом. Их причины по логам не позволяют автоматически заключить,
что это ошибка только теста или только численной реализации.

Исторические результаты на 0,5 с приводятся отдельной таблицей с пометкой
**СТАРЫЕ**; новая серия 50 мс не повторяет их длительность и не заменяет их
разброс. Расчёт 150 модельных секунд этой сети не выполняется. Изменения
активности, весов, плотности событий и скользящих журналов могут нарушить
линейную экстраполяцию. ThreadSanitizer и длительная ручная GUI-сессия
этой серией не подтверждаются.

## Команды

`run_stages.py` печатает план без запуска; фактический синтаксис параметров
проверяется через `python -B performance/20261019_stage_review/run_stages.py --help`.
Измерения, сборки и CTest должны выполняться строго последовательно.
Нельзя повторно использовать каталог уже сохранённых измерений.

После завершения всех процессов и появления `measured/runs.json` и `ctest.xml`:

```powershell
python -B performance/20261019_stage_review/build_report.py --write
```

Команда создаёт `REPORT_RU.md` и компактную машинную сводку из завершённых
записей. Без `--write` показывает отчёт в stdout. При неполных сериях или
отрицательных свидетельствах сравнения она должна завершиться ошибкой,
а не публиковать неподтверждённый итог.
