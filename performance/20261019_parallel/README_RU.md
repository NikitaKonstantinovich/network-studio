# Проверка параллельного решателя: методика воспроизведения

В этом каталоге сохранены последовательные измерения, исходные сравнения и
сценарии воспроизведения. Итоговые выводы находятся в `REPORT_RU.md`, подробные
таблицы завершённых записей — в `MEASUREMENTS_RU.md` и `summary.json`.
Предыдущие отчёты и замороженный `../20261019_runner/runner-release/`
используются только для чтения; перезаписывать или пересобирать этот reference
нельзя. Параллельность внутри решателя проверяется отдельно от ранее выполненного
переноса однопоточного решателя из GUI в worker.

## Происхождение сетей

`prepare.py` берёт точные байты `../20261019_single_thread/fixture.json`, сверяет
SHA-256 с прежним provenance и создаёт варианты двух нагрузок на 5/50/100/500 мс:

- `burst`: прежняя сеть из 500 Ижикевич (400 E / 100 I), 15 013 TM-синапсов,
  мультипликативная STDP, глобальный шум σ=5, seed=706. Полная версия 500 мс —
  точная байтовая копия предыдущего fixture. Это производная сохранённого опыта,
  а не найденная исходная сеть с ровно 15 041 синапсом.
- `quiet`: тот же граф, модели, веса, начальные состояния и запись; изменены
  только название, необходимая длительность и σ глобального шума с 5 до 0.
  У всех исходных нейронов уже нулевые DC/импульсы, индивидуальный шум выключен,
  общих стимуляторов нет. Скрипт проверяет эти предусловия. План этапов сохранён,
  но benchmark не активирует этапы. Это синтетический контроль без внешнего
  возбуждения; фактическое отсутствие спайков нужно подтвердить экспортом.

Шаг в обоих случаях 25 мкс, интервал шума 1 мс, интервал записи 2 мс.
Длительность означает **реальный интегрированный интервал**, а не подмножество
строк полного прогона: 5/50/100/500 мс соответствуют 200/2000/4000/20000 шагам.
Короткий burst содержит начальный переходный процесс; его время нельзя линейно
экстраполировать на 500 мс или на устойчивый режим. В quiet шум выключен,
поэтому её ускорение не доказывает ускорения генерации шума.

`provenance.json` содержит полный список изменений, хеши и проверку четырёх
reference EXE по предыдущему `build_manifest.json`. Большие JSON в `fixtures/`
генерируются воспроизводимым скриптом и исключены из Git; при передаче измерений
нужно приложить их или запустить тот же генератор с неизменённым source.

## Последовательность

Подготовка не запускает вычисление:

```powershell
python performance/20261019_parallel/prepare.py
python performance/20261019_parallel/capture_environment.py
python performance/20261019_parallel/measure.py --phase smoke --out performance/parallel-smoke
```

Последняя команда **только печатает план**. После разрешения основного процесса
добавить `--execute`; каталог вывода должен быть новым. По умолчанию это один
прогон quiet/burst для каждой настройки 1, 2, 4, 8 и Auto (число 0), плюс
один запуск замороженного последовательного reference на каждой нагрузке.
Скрипт использует общий `performance/.benchmark.lock`. Сборки, тесты и другие
измерения одновременно запускать нельзя.

Ступени выполняются отдельно; конкретные завершённые серии и число повторов
определяются их `runs.json`, а не этим общим планом:

1. `--phase smoke`: 5 мс, по одному запуску; проверить аргументы, конечное время,
   экспорт, checkpoint и использование потоков. Это не доказательство ускорения.
2. `--phase diagnostic`: 50 мс, по одному запуску; выявить заведомую деградацию
   и проверить плотный начальный поток событий.
3. `--phase intermediate`: 100 мс, по одному запуску; оценить целесообразность
   полной матрицы, сохранив одинаковую длительность для всех thread counts.
4. `--phase full`: 500 мс, сначала по одному запуску 1/2/4/8/Auto. После этого
   `--repeat 3 --threads 1 4 0` (пример) для выбранных настроек; точный выбор
   делается по полученным данным и бюджету. При наличии времени — три полных
   повтора всей матрицы, а не изменение длительности только медленных вариантов.

При ограниченном бюджете целесообразен план 50 мс × 3 повтора полной матрицы,
затем 100/500 мс для 1 потока и выбранных режимов. Это 32 процесса для серии
50 мс (по одному frozen и 15 новых на каждую нагрузку); для 500 мс и
`--threads 1 4 0 --repeat 1` — 8 процессов. Реальное время всей серии заранее
не обещается: после коротких ступеней его оценивают по измеренным секундам.
Сокращение списка режимов должно быть отражено в отчёте.

`--workloads quiet` или `--workloads burst` позволяет запускать нагрузки отдельно.
`--mode cli` измеряет direct solver benchmark; `--mode runner` дополнительно
измеряет controller и получение конечного снимка с фиксированными 10 Гц/1 мс.
Настройки режимов нельзя смешивать при расчёте ускорения.

```powershell
python performance/20261019_parallel/measure.py --phase full --mode cli --new-dir build/parallel/Release --out performance/parallel-full --repeat 1 --execute
python performance/20261019_parallel/measure.py --phase full --mode runner --new-dir build/parallel/Release --out performance/parallel-runner --threads 1 4 0 --repeat 3 --execute
```

API согласован: direct benchmark принимает `CONFIG OUTPUTDIR [THREADS]`, runner
benchmark — `CONFIG OUTPUTDIR [HZ] [CONSUMER_MS] [THREADS]`; Auto обозначается 0.
Замороженным EXE дополнительный аргумент не передаётся. Итоговые JSON должны
содержать как запрошенное, так и **фактически выбранное** число потоков. Нельзя
называть Auto «8 потоками», исходя только из характеристик CPU. Настройки
параллельности — политика исполнения; если они входят в сериализуемый config,
контракт сравнения нужно пересмотреть до измерений, а не молча исключать поля.

## Измеренная калибровка и Auto

`calibration_50ms/runs.json` содержит 26 завершённых запусков: по три повтора
1/2/4/8 для quiet и burst, плюс по одному frozen reference. Auto в этой серии
не запускался: политика выбиралась после калибровки. `crossover_v2/runs.json`
содержит 36 завершённых запусков на 5 мс: три размера × четыре настройки ×
три повтора. Измерения на 20 мс для crossover из наличия готовых fixture
не следуют. Повторить эти серии в **новых** каталогах можно командами:

```powershell
python -B performance/20261019_parallel/measure.py --phase diagnostic --threads 1 2 4 8 --repeat 3 --new-dir build/parallel/Release --out performance/20261019_parallel/reproduce_calibration_50ms --execute
python -B performance/20261019_parallel/crossover.py --duration .005 --threads 1 2 4 8 --repeat 3 --new-dir build/parallel/Release --out performance/20261019_parallel/reproduce_crossover_v2 --execute
```

Текущая политика Auto применяется только к сетям, допущенным к параллельному
пути: все нейроны Izh, все синапсы TM, астроцитов нет. Учитывается размер
массива синапсов, включая отключённые связи, а не число событий текущего шага.

| Конфигурация | Предел Auto до ограничения оборудованием |
|---|---:|
| Менее 2048 синапсов либо неподдерживаемые модели | 1 |
| 2048–8191 синапсов, поддерживаемая сеть | 4 |
| Не менее 8192 синапсов, поддерживаемая сеть | 8 |

Из допустимых чисел 1/2/4/8 выбирается наибольшее, не превышающее этот предел
и `std::thread::hardware_concurrency()`. Если ОС не сообщает число потоков
(возвращает 0), выбирается 1. Число включает вычисляющий поток-координатор.
Явные настройки 1/2/4/8 сохраняют прежний смысл; ограничение по hardware
concurrency действует для Auto. Неподдерживаемая сеть использует serial path
при любой настройке, а requested/effective в метриках показывают различие.

На основной 500-нейронной сети восемь потоков дали меньшую медиану, чем четыре:
burst 4,389 против 5,695 с, quiet 2,521 против 2,981 с на 50 модельных мс
(n=3, конкретные сборка/разброс — в calibration). В малых синтетических сетях
медианы восьми потоков также ниже, но выигрыш для 64/128 нейронов невелик
относительно наблюдаемого разброса: 0,0586 против 0,0626 с и 0,1023 против
0,1143 с. Поэтому для меньших поддерживаемых сетей выбрано четыре потока
как более сдержанная политика использования ресурсов. Это не доказательство
оптимальности четырёх потоков и не статистическое доказательство равенства
режимов; часть наблюдаемых диапазонов пересекается, а выборка мала.

Порог 2048 является консервативным условием допуска; его оптимальность для
всех сетей ниже порога не измерялась. Калибровка относится к указанному Intel
CPU и Windows. Auto остаётся эвристикой: ARM, другие CPU, гибридные ядра,
SMT, affinity/контейнерные ограничения, иная активность и загрузка системы
могут изменить лучший выбор. Значение hardware_concurrency не измеряет
доступную производительность. На другой машине следует повторить серию
и при необходимости использовать явную настройку, не обещая ускорения.

Ранние `stage4_smoke` и другие исторические серии могут показывать Auto→1:
это результат прежней политики в той сборке, не результат новой Auto.

## Синтетические сети около порога включения

Дополнительный `crossover.py` строит 64/128/256 Izh с ровно 32 различными
пресинаптическими источниками на каждый нейрон, без самосвязей: соответственно
2048/4096/8192 TM-синапсов. Это обеспечивает действительное выполнение текущего
условия допуска (не меньше 2048, только Izh/TM, нет астроцитов); во время замера
скрипт дополнительно требует `effective_threads == requested_threads` для
1/2/4/8, поэтому fallback не будет ошибочно принят за параллельный запуск.

Популяции E/I — 51/13, 102/26 и 204/52. Нейроны копируются из исходных E/I;
каждая новая связь копирует все кинетические и STDP-параметры одной исходящей
связи соответствующего исходного пресинаптического нейрона. Сохраняются
положительные E-веса и multiplicative STDP, отрицательные I-веса без STDP.
Источники выбираются детерминированным SHA-256 ranking с seed706; прототип веса
выбирается независимым hash. Никакие состояния checkpoint не переносятся:
ресурсы и следы инициализирует штатный конструктор. Шум σ=5/1 мс, шаг 25 мкс,
запись 2 мс; recording indices проверены. Этапы, общие стимуляторы и старые
метаданные генерации 500 нейронов удалены.

Это **синтетические тесты накладных расходов**, не лабораторные сети и не
сохранение динамики исходной популяции. Предусмотрены настоящие интервалы
5 мс (200 шагов) и 20 мс (800 шагов), а не вырезка результатов большого опыта.
Параметры, topology rule и исходные индексы находятся в `crossover_provenance_v2.json`.
Используются файлы `fixtures/crossover_v2_*.json`. Первая версия добавляла пустой
массив `stimulators`, но пропускала обязательные для этого раздела поля;
первая попытка завершилась ошибкой парсинга до расчёта. V2 явно задаёт
`next_stimulator_id="1"` и `activity_horizon=1` (штатные значения). Исходные
v1-файлы, `crossover_provenance.json` и каталог неудачной попытки сохранены.
Все шесть v2-файлов (три размера, два интервала) проверены штатным
`network_studio_cli --config FILE --save NEW_FILE`: код выхода 0, без создания
Simulator и без интегрирования. Команды, SHA и результаты сохранены в
`crossover_validation_v2/validation.json`; проверено, что v1 не изменились,
а конфигурации v2 отличаются только двумя добавленными полями.

```powershell
python performance/20261019_parallel/crossover.py --prepare
# Только план; 36 новых процессов: 3 размера × 4 thread counts × 3 повтора.
python performance/20261019_parallel/crossover.py --duration .005 --repeat 3 --out performance/parallel-crossover
# После отдельного разрешения добавить --execute.
```

Все повторы и thread counts каждого размера сравниваются побайтно с первым
serial запуском той же новой сборки (CSV и весь checkpoint). Используются тот
же lock и sampler памяти, что у основной серии. Скрипт не запускает сборку.

## Эквивалентность

Первый запуск новой сборки с 1 потоком сравнивается с frozen reference на
**том же файле конфигурации**: все `result_*.csv` побайтно, весь checkpoint
офлайн через `compare_checkpoint.py`, исключая только документированные build
ID и зависимый checksum, с проверкой обеих исходных checksum, схемы, алгоритма
и config. Это чтение файлов, не загрузка несовместимого checkpoint.

Затем 2/4/8/Auto и остальные повторы сравниваются с `threads_1/run_1` новой
сборки: весь checkpoint и CSV должны совпасть без исключений и без допуска.
Все состояния, ресурсы, следы STDP, веса, очереди и служебные поля, которые
сохраняет checkpoint, участвуют в этом сравнении. Различия параметров/чисел
нельзя спрятать за изменением checkpoint compatibility. Штатный loader и
checkpoint/resume проверяются отдельными существующими тестами.

Для каждой записи скрипт проверяет фактическое конечное модельное время.
Счётчик спайков/доставок нужно отдельно свести в отчёте, подтвердив характер
quiet/burst. Сравнение bytes этого опыта не доказывает отсутствие любых гонок;
нужны также модельные тесты, стресс различного числа потоков, lifecycle,
все правила STDP, задержки/совпадающие события и checkpoint/resume.

## GUI, runner и продолжение CLI

`integration.py` выполняет отдельную последовательную проверку на одной
конечной сборке и `burst_50ms.json`: direct serial reference; скрытые native
GUI 1/Auto с 10 Гц; runner Auto с 10/1/60 Гц; CLI до 25 мс на двух потоках
и штатный resume checkpoint до 50 мс на восьми. Результаты GUI, runner и
завершённого resume должны совпасть с direct reference: десять CSV и полный
checkpoint без исключения build ID. Промежуточный 25-миллисекундный prefix
не сравнивается с полным 50-миллисекундным состоянием; его checkpoint
используется штатным loader следующего процесса.

```powershell
# Только план; --execute разрешает последовательный запуск восьми процессов.
python -B performance/20261019_parallel/integration.py --new-dir build/parallel/Release --out performance/20261019_parallel/reproduce_integration --threads 0
```

`integration.json` отделён от обычного `runs.json`. Сводка не добавляет эти
запуски повторно в основную матрицу и не объединяет разные таймеры. Direct
имеет solve time, GUI/runner — wall до финального состояния с обменом
snapshot; CLI prefix/resume здесь имеет только **время всего процесса**,
включая загрузку, сохранение и экспорт. Переданные delta-записи не считаются
уникальными научными событиями. Число helper threads, частота публикации,
паузы/продолжения и сериализация не должны менять численные результаты.

GUI benchmark создаёт скрытое настоящее окно Win32/DX11 и вызывает Present(1).
`present_occluded`, `present_ok`, renderer и времена CPU сохраняются отдельно.
Это измерение скрытого native GUI с его snapshot/render loop, не ручная
интерактивная сессия и не измерение времени GPU. Окклюзия может влиять на кадры
и ожидания. Тесты открытого GUI и поведение при пользовательских действиях
проверяются отдельно; по результату скрытого окна нельзя обещать ту же
частоту кадров в видимом приложении.

## Память

`measure.py` опрашивает собственный дочерний процесс через Windows
`GetProcessMemoryInfo` (по умолчанию раз в 100 мс; `--memory-ms`). Никакой код
не внедряется в child, приоритет/affinity не меняются. Сохраняется `memory.json`
с временным рядом и именами Windows counters:

- `PeakWorkingSetSize`: максимум resident working set, накопленный ОС до
  последнего успешного запроса. Это ближе к пику RSS, но не объём private heap.
- `PrivateUsage`: текущий private commit; максимум опрошенных значений может
  пропустить короткий пик и не выдаётся за точный lifetime peak.
- `PeakPagefileUsage`: отдельный OS counter commit usage; он не подменяется
  именем RSS. Результат финального запроса после выхода сохраняется явно.

Эти значения относятся ко **всему процессу**, включая загрузку, модель,
thread stacks/пулы, snapshots, экспорт и checkpoint. Таймер ядра исключает часть
этих этапов. Поэтому рост памяти можно сравнивать между одинаковыми режимами,
но нельзя приписать весь пик только параллельному kernel без дополнительного
внутреннего измерения. Дочерние процессы child не учитываются; benchmark их
создавать не должен. Накладные расходы опроса присутствуют во всех новых сериях
одинаково; старые времена без sampler напрямую не являются новой контрольной
серией для вычисления ускорения.

## Отчёт

Для каждой нагрузки и длительности отдельно: requested/effective threads,
число повторов, медиана/min/max/SD wall и модельные с/реальную с, ускорение
относительно **новой 1-thread сборки**, checksum comparison, фактические события,
peak working set и sampled private commit. Замороженный reference показывает
регрессию против прежней реализации; результаты прежней исторической серии
можно приводить лишь как контекст из другого момента времени.

В `environment.json` записываются CPU, логические процессоры, ОС, RAM и power
scheme. Это не контроль температур/частот/фоновых приложений. Зафиксировать
новые EXE, compiler/flags, исходники и checkpoint build ID после последней
пересборки. Время измерять без profiling/fast-math; порядок суммирования и
численная точность должны сохраняться. Не обещать линейного масштабирования;
на тихой сети расходы синхронизации могут превысить полезную работу.
